# PRD-001：并行 PRD 编排与全局治理无感化

## 背景与问题

Harness Lite 当前能够维护 `principle → PRD → SPEC → 实现 → deviation → 验收证据` 的纵向治理链，但现行生命周期以单一串行 iteration、固定分支和一次最终提交为前提，无法自然支撑多个 PRD 在同一 Codex 项目中并行推进。

目标用户希望只描述产品需求，不必理解或显式指定 worktree、分支、路径和治理文档操作。Harness 应自动判断需求属于新 PRD 还是既有 PRD、应采用何种起草路径、是否需要独立工作区，以及何时进入候选和集成验证。同时，这种无感化不能弱化全局产品原则、过程证据、用户授权或 Git 状态透明度。

需要解决的核心矛盾包括：

- 单个活跃 PRD 应保持低开销，直接使用主工程 checkout；第二个及后续 PRD 出现时才按需隔离。
- 第一个 PRD 可能仍有未提交改动；新增 PRD 不得提交、stash、移动或吸收这些改动。
- 每个并行 PRD 都必须继续独立经历 PRD、SPEC、实现、偏差处置和验收证据，而不是只获得文件隔离。
- `principle.md` 必须继续提供单一全局产品控制；`progress.md` 必须让并行过程可追溯，又不能反向成为批准来源。
- 多个独立候选验证通过，不代表它们与最新 main 组合后仍然成立；需要串行集成和二次验证。
- 自动化可以低打扰，但 worktree、branch、commit、merge 和 push 等 Git 状态变化不能被隐藏。
- 并发、崩溃、dirty/untracked/ignored 文件和运行时资源会使简单 shell 编排产生重复操作、串扰或数据丢失。

若不演进，用户必须手工切换目录和 Git 状态，多个 Codex 任务容易写错工作区；并行候选可能在治理文件、原则、数据库、端口或 main 集成时互相污染；最终结果也难以证明仍符合总体原则与批准基线。

## 产品目标

1. 用户只描述需求，Harness 自动完成需求路由、治理路径判断和执行拓扑选择。
2. 支持一个 Local PRD 与任意多个独立 worktree PRD 并行存在，并保持任务、文件、运行时和写入归属隔离。
3. 让每个 PRD 都完整服从全局 principle、同号 PRD/SPEC、deviation 和验收证据链。
4. 让 `progress.md` 成为可合并、不可静默改写的过程审计记录，并由权威事实确定性重建 README 路由。
5. 通过 latest-main merge train 和集成复验，保证进入 main 的结果与获准候选一致。
6. 将自动动作分成静默自动、明确通知和明确确认三档，在低打扰与 Git 透明之间建立稳定边界。
7. 在任务中断、Codex 重启或编排步骤部分失败后可幂等恢复，不重复分配、提交、记录事件或删除用户状态。
8. 保持现有 Harness 项目的原则、历史迭代、批准和验收证据可读取、可验证，不重写既有历史。

## 范围内需求

### R-001-01：Principle 单一全局产品控制

所有活跃 PRD、Codex 任务、worktree、候选和集成结果必须服从 main 上同一套已批准原则。代理不得推断、静默新增、自动并集或按合并顺序裁决原则。

原则变更必须绑定精确文本、批准证据和生效身份；系统必须识别所有开放 PRD 的原则基线与影响。原则漂移未完成影响审计前，受影响 PRD 不得继续候选化或集成。

### R-001-02：每个 PRD 保持完整纵向治理

并行只改变执行拓扑，不改变权威链。每个 PRD 必须独立维护产品范围、验收、实施规格、as-built 偏差、验证证据和最终验收。批准顺序仍为：已批准 principle > 已批准 PRD > 已批准 SPEC；deviation 和 progress 都不能提供实施授权或原则例外。

### R-001-03：Progress 过程控制与历史可追溯

`progress.md` 必须记录每个 PRD 的创建、批准、工作区状态变化、候选生成与失效、验证、集成、决定和关闭。事件必须具有全局唯一身份、明确 PRD/operation 归属、因果关系和证据引用；重试不得重复记录，纠错不得改写旧事件。

多个 worktree 的 progress 变更在集成时必须按事件语义合并：同 ID 同内容幂等去重，同 ID 异文硬阻塞，事实冲突全部保留并通过新的明确决定解决。progress 始终是历史证据，不是当前规范权威。

### R-001-04：README 与全局状态为可重建派生路由

L0/L1 README 必须从 principle、PRD/SPEC/deviation 状态、progress 事件和 Git refs 确定性重建，展示每个 PRD 的 Local/worktree 位置、治理门禁、依赖、候选和集成状态。分支副本不得通过普通 ours/theirs 合并决定全局状态。

### R-001-05：治理路径、执行拓扑与授权分离判断

系统不得用一个“需求大小”开关同时决定文档深度、worktree 和实施权限。每次请求必须分别判断：

1. 治理路径：按清晰度、产品影响、风险、可逆性和跨系统协调选择 grill、PRD/SPEC 联合草拟或 PRD-first。
2. 执行拓扑：按活跃写入数、依赖关系、dirty 状态和资源冲突选择 Local、独立 worktree、stacked 或必须串行。
3. 授权状态：独立确认 PRD 批准、SPEC 批准、实施授权、集成授权和最终验收。

分类只能决定下一步流程，不能推断任何批准。执行中发现 schema、权限、安全、隐私、迁移、不可逆或跨系统风险时必须升级门禁。

### R-001-06：单 PRD Local 低开销路径

从空闲状态启动一个需要写入实现的 PRD 时，直接使用主工程 checkout：

- 不额外创建 linked worktree；
- 不因 Harness 自动创建功能分支、commit 或 stash；
- 记录该 PRD 对当前任务、可写路径、未提交改动和 committed main baseline 的逻辑归属；
- 若已有不属于该 PRD 的 dirty 状态，阻止自动归属并请求处理。

### R-001-07：第二个及后续 PRD 懒创建 worktree

第二个独立 PRD 获得实施授权时，Harness 自动从明确的 committed main 创建分支和 linked worktree。第一个 PRD 保持原目录、原任务、index、未提交文件和运行上下文不变；不得提交、stash、复制或移动其状态。第三个及后续 PRD 各自获得独立工作区。

第一个 Local PRD 可以继续停留在 main 分支；只有当另一个 PRD 必须先推进 main 时，才在严格 preflight 后将第一个 PRD 原地绑定到独立分支。该动作不得提交、stash 或移动文件，并必须明确通知用户。若第一个 PRD 自己先完成，则无需为了并行形式先搬迁或补建 linked worktree。

并发数从多个降为一个时，幸存 PRD 原地完成，不自动回迁；全部活跃 PRD 归零后，下一项单 PRD 才重新使用 Local 模式。

### R-001-08：PRD 身份、任务、路径和运行时隔离

每个可写 PRD 必须拥有唯一 iteration ID、Codex 主任务、绝对可写路径、明确 baseline/branch 状态、单写入者 lease 和运行时资源命名空间。任何 mutation 前必须校验 PRD、root、path、branch、base 和 lease generation；不一致时在写文件前停止。

worktree 只提供 Git 文件隔离，不能被宣称为安全沙箱。项目可为端口、数据库/schema、日志、容器网络/volume、缓存和测试账号提供独立命名空间；Harness 不得盲目共享可变依赖目录或共享开发数据库。

### R-001-09：依赖、冲突和基线显式化

每个 PRD 必须声明 `depends_on`、`conflicts_with`、集成目标、共享契约/schema 和资源 claim。独立 PRD 从 committed main 起步；依赖另一 PRD 的工作只能从稳定 candidate/ref 起步，不得隐式读取另一工作区的 dirty tree。依赖未稳定时可以继续产品/规格工作，但相关实现或集成必须阻塞。

### R-001-10：候选、Merge Train 与 latest-main 复验

每个 PRD 的 feature candidate 必须绑定已批准 PRD/SPEC、实现 tree、验证证据和偏差处置。feature 验证只证明该 PRD 在自身基线成立。

多个候选可以并行准备，但必须通过单一串行 merge train：在最新 main 上按依赖和优先级逐个构造 integrated candidate，先完成 principle gate、progress 语义导入和 README 重建，再运行跨 PRD/全局验证。main、原则或依赖变化后，旧集成证据失效；不得把独立 worktree 的绿灯直接等同于可进入 main。

### R-001-11：低打扰但透明的 Git 交互

生命周期动作必须归入以下等级：

- `Silent`：只读扫描、分类、确定性派生、验证和已授权操作的幂等恢复。
- `Notify`：明确告知后执行范围可证明、可恢复的本地状态变化，并在完成后报告结果。
- `Confirm`：执行前展示精确范围并等待用户确认。

任何新 worktree 的创建或移除必须在执行前明确说明 PRD、原因、base、branch、路径、对其他 PRD 的影响和是否涉及远端，并在完成后报告结果。安全 preflight 通过时创建可以是非阻塞通知；存在 dirty/路径/归属异常时升级为确认。

所有 Git commit 必须在执行前展示 branch、提交范围、message、验证结果和明确排除项并获得确认，完成后报告 hash 与“尚未 push”。push 必须与 commit 分离，展示 remote、source/target ref、提交范围和 force 状态并单独获得确认。推进 main、merge/rebase/cherry-pick、删除分支、历史改写和破坏性清理同样不得静默执行。

### R-001-12：幂等编排、保守恢复和安全清理

每个有写入的编排流程必须具有 operation ID、预期 refs、可审阅计划、持久 journal 和原子阶段状态。并发 ID/ref 分配、writer lease、principle 变更和 merge train 必须使用单协调者或 compare-and-swap，避免双写。

崩溃恢复不得依赖自动 stash。系统只能清理由本 operation 创建、仍与 manifest 匹配、无活动 writer/process 且没有未处置 untracked/ignored 资产的对象。未知 orphan、dirty worktree 和失败后的源路径必须保留并进入 reconcile，不得 force 删除。

### R-001-13：现有项目兼容与可审阅迁移

升级不得改写既有 principle、已验收迭代、progress 历史、deviation 或 final refs。旧串行项目必须先得到 dry-run 迁移清单；已完成迭代保持原样，活跃 dirty 迭代默认继续旧生命周期或经用户明确授权后迁移。旧事件 ID 原样保留，新并发事件采用新身份规则。

### R-001-14：用户可理解的全局体验

用户通过 PRD/任务而不是文件路径工作。正常情况下只看到：状态卡、重要动作通知和产品决策/授权卡；不需要执行 `cd`、worktree、branch 或 merge 命令。系统必须能够回答“为什么选择这条治理路径、为什么创建 worktree、当前服从哪版原则、下一门禁是什么”，并提供关联证据。

## 验收标准

- **AC-001-01（全局原则）**：两个以上 PRD 并行时提出 principle 变更，系统要求精确文本批准，标记所有开放 PRD 的 principle drift；完成影响审计前，受影响 PRD 无法候选化或集成。
- **AC-001-02（纵向治理）**：任一 PRD 缺少 PRD/SPEC 批准、实施授权、AC 证据或偏差处置时，即使代码测试通过，也无法形成可集成候选。
- **AC-001-03（Progress 并发）**：两个 worktree 同时追加事件并模拟重试，集成后每个事件只出现一次且归属正确；同 ID 异文被阻塞，历史未被重排或改写。
- **AC-001-04（README 重建）**：存在一个 Local PRD、两个 worktree PRD 和一个集成候选时，删除 managed 派生区后能够从权威源重建相同的 L0/L1 状态与下一门禁。
- **AC-001-05（三轴分类）**：小且明确、表面小但含权限/数据歧义、明确但高影响三类场景分别选择联合草拟、grill、PRD-first；三者均未自动获得实施授权，worktree 选择仅由执行拓扑决定。
- **AC-001-06（单 PRD Local）**：从空闲状态启动 PRD-A 后不产生额外 worktree、隐式 branch、commit 或 stash，同时可报告 A 的 committed main baseline 和 dirty 归属。
- **AC-001-07（第二 PRD）**：A 保持未提交改动时启动独立 PRD-B，B worktree 内容等于 committed main 且不包含 A 的改动；A 的文件、index、路径、任务和历史保持不变。
- **AC-001-08（三个以上 PRD）**：至少三个 PRD 同时实现时，每个 PRD 具有唯一任务、路径、writer lease 和运行时命名空间；一个 PRD 的失败不改变其他 PRD 的未提交状态。
- **AC-001-09（延迟释放 main）**：B 先于 A 集成时，系统在不提交、不 stash、不移动文件的情况下为 A 原地补充分支归属；转换前后 A tree 与 cwd 一致，并有清晰通知和 progress 证据。
- **AC-001-10（无回迁抖动）**：并发从三个降为一个时，幸存 PRD 保持原路径直至完成；全部关闭前不为满足数量阈值自动搬迁。
- **AC-001-11（任务路由门禁）**：故意使任务指向错误 worktree 或使用过期 lease generation，系统在任何文件写入前停止并报告预期与实际身份。
- **AC-001-12（依赖基线）**：PRD-C 声明依赖 PRD-B 时，B 未形成稳定 candidate 前 C 不得消费其实现；B candidate 更新后 C 被标记 baseline stale 并重新验证。
- **AC-001-13（Merge Train）**：两个候选以任意顺序准备后，系统按依赖/队列逐个基于最新 main 集成；每次 main 前进都绑定 exact integrated tree 和完整验证，未验证树无法进入 main。
- **AC-001-14（Git 透明）**：worktree 创建前后均有聚合通知；commit 和 push 各自有独立确认卡。commit 结果明确 hash 与未 push 状态，push 结果明确远端 ref；没有原始 Git 命令噪声。
- **AC-001-15（异常恢复）**：在 ID 预留、branch 创建、worktree 创建、事件导入和 main 集成各阶段注入中断，重启 reconcile 后不会重复分配、重复事件、重复 commit 或丢失 dirty/untracked/ignored 状态。
- **AC-001-16（历史兼容）**：升级包含已完成串行迭代的项目后，旧原则、PRD/SPEC、deviation、progress、README 路由和验收证据仍可验证，历史内容与身份未被重写。

## 已批准的长期原则基线

用户已于 2026-08-11 批准以下精确文本；权威版本已同步到全局 `principle.md`：

### P-001：自动化服从产品权威

任何无感化、并发编排或验证结果都不得替代已批准原则、明确产品决定、实施授权和最终验收。遇到冲突时先保持权威边界，再追求自动化完成率。

### P-002：并行不得牺牲可追溯性

每个 PRD 无论处于 Local、worktree 或集成阶段，都必须能从产品意图追溯到规格、实现、偏差、验证和最终进入 main 的精确结果；无法证明归属的状态不得自动合并或清理。

### P-003：Git 状态变化透明

Harness 可以自动规划和执行已授权的机械步骤，但不得隐藏 worktree、branch、commit、main 更新或 push 等对用户有意义的 Git 状态变化；外部、破坏性或权威性变化必须获得精确确认。

## 非目标

- 替代 Issue、Sprint、排期、人员协作或完整项目管理系统。
- 把 worktree 宣称为权限沙箱、容器或完整运行环境隔离。
- 自动判断两个 PRD 在产品语义上一定独立，或自动解决代码、schema、原则和验收冲突。
- 内置所有技术栈的包管理、Docker、数据库、secret、CI、云资源或部署平台；本轮只定义项目 adapter 契约。
- 自动把一个 PRD 的 dirty tree 作为另一个 PRD 的隐式依赖。
- 自动批准 PRD/SPEC、接受残余偏差、修改原则或完成最终验收。
- 默认 push、创建远端 PR、部署、迁移共享数据库或创建付费外部资源。
- 自动 stash/reset/clean/force、强删 dirty worktree、重写已验收历史或静默改写 progress。
- 因并发数量下降而搬迁仍在活动的 worktree。
- 在本轮提供跨多个相互独立 Git 仓库的统一 merge train。

## 产品约束

- `harness/` 继续作为唯一可编辑的项目治理事实源；本机 operational registry 不得成为不可恢复的规范权威。
- 已批准 principle > 已批准 PRD > 已批准 SPEC 的权威顺序不可降低。
- 每个 iteration 保持同号完整 bundle；ID 唯一且永不复用。
- progress 只追加历史事件；README 只做派生路由；deviation 只记录完成后的 as-built 事实。
- Local PRD 的 dirty 状态必须能与既有用户改动明确区分；归属不明时不得自动进入并行写入。
- 新 worktree 只能基于明确的 committed main 或声明依赖的稳定 candidate，不得隐式采用当前 cwd 的 dirty HEAD。
- 每个 PRD 同一时刻只有一个主写入者；全局 ID、原则和 merge train 具有唯一协调权。
- 自动操作必须幂等、可解释、可恢复，并在每次 mutation 前检测状态漂移。
- 网络、push、远端 PR、依赖安装、共享数据迁移和部署继续受独立授权控制。
- Windows 路径包含空格、Codex 重启或任务切换时，PRD 路由和恢复仍必须成立。
