# Harness Lite 项目原则

## 文档定位

本文件保存跨迭代、长期有效且经用户明确批准的产品/项目原则。原则约束 PRD 与 SPEC；不得为了配合某次实现而无痕改写。

## 已批准原则

### P-001：自动化服从产品权威

任何无感化、并发编排或验证结果都不得替代已批准原则、明确产品决定、实施授权和最终验收。遇到冲突时先保持权威边界，再追求自动化完成率。

### P-002：并行不得牺牲可追溯性

每个 PRD 无论处于 Local、worktree 或集成阶段，都必须能从产品意图追溯到规格、实现、偏差、验证和最终进入 main 的精确结果；无法证明归属的状态不得自动合并或清理。

### P-003：Git 状态变化透明

Harness 可以自动规划和执行已授权的机械步骤，但不得隐藏 worktree、branch、commit、main 更新或 push 等对用户有意义的 Git 状态变化；外部、破坏性或权威性变化必须获得精确确认。

## 冲突处理

- 原则与 PRD 冲突时，暂停冲突范围并请求用户决定。
- PRD 与 SPEC 冲突时，以已批准 PRD 为基线，回到需求或规格批准门。
- 实现前已知的变化必须修订并重新批准受影响的 PRD/SPEC；实现后的 deviation 只记录事实差异，不构成例外权威。

## 变更控制

- 只有用户明确批准后才能新增、修改、废止原则或调整优先级。
- 保留原批准语义，通过变更记录说明变化；不要无痕重写历史基线。
